# Proposed bulk-edit acceptance contract

Status: proposal only. No product code, UI, API or database behavior has been verified. Apply $senior-frontend to the existing React/TypeScript flow and $api-design-reviewer to the existing API contract.

1. Selection and edits: show the exact target count/scope before submission. Decide whether selection means explicit row IDs or all filtered rows, including pagination. Changes apply only to selected targets and explicitly edited fields; omitted fields remain unchanged. Define clearing/null separately from leaving a field unchanged, and define mixed-value presentation. Empty selection and no-op changes send no mutation.
2. Form behavior: reuse the existing components and validation conventions. Use native buttons, associated labels and field errors, visible keyboard focus, and a defined focus destination after validation, cancellation and completion. Show loading, empty, permission-denied, error and success states. Cancel before submission writes nothing. Prevent duplicate UI submission while pending; on a timeout show an uncertain outcome rather than false success or an unqualified retry.
3. Trusted API checks: the existing server validates allowed fields, values, target scope and batch bounds and authorizes every affected record/field in the actor's existing tenant context. Hidden UI controls are insufficient. Unauthorized/out-of-scope rows must not be changed. Establish expected error mapping without inventing a new authentication or naming convention.
4. Mutation semantics: choose all-or-nothing versus explicitly reported per-row results before implementation. Define stale/deleted targets, concurrent edits, batch limits and retry/idempotency guarantees. If all-or-nothing is selected, a rejected row leaves the whole batch unchanged; if partial success is selected, return explicit succeeded/failed IDs and ensure the UI never reports total success for a partially failed batch. Do not silently overwrite a newer edit; define the chosen conflict strategy. Preserve existing PostgreSQL integrity rules.
5. Compatibility: existing single-record callers retain their request/response/error behavior. Compare required fields, types, enums, nullability, authentication and pagination before/after. For rolling deployment, establish new-server/old-client and old-server/new-client behavior where required; evaluate real callers/SDKs rather than a convention score.
6. Evidence required for acceptance: use existing tooling with isolated authorized fixtures to demonstrate a successful batch changes only selected fields/rows; invalid input and forbidden tenant/record cases do not mutate protected state; stale/deleted target and concurrency cases match the chosen policy; repeated/timeout requests match promised retry semantics; keyboard/error/pending/cancel states work; existing callers remain compatible. Record semantic responses and durable-state evidence, actual results and skipped prerequisites. No SQL or product tests were executed in this setup exercise.

Missing inputs: source and dependency versions; dashboard selection/filter/pagination behavior; entity and editable-field rules (including mixed values and null); current API routes/schema/error/auth contract and callers/SDKs; backend framework and test tooling; PostgreSQL version/schema/invariants and transaction boundaries; roles/tenant permissions; batch maximum/expected volume; atomicity, conflicts, retry/idempotency and audit/undo decisions; device/network, accessibility owner/target, and any performance budgets; safe isolated fixtures/environment and permission for future tests. These inputs must turn conditional proposals above into concrete expected outcomes.

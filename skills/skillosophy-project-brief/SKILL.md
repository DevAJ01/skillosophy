# Project Brief

Define the project the user actually wants to build, and the working principles that should govern its decisions. Inspect existing project guidance and artifacts before asking the user to repeat information. For a new folder, use the user's request as the starting evidence.

Separate the desired user outcome from the proposed feature and technology. Identify who will use the result, what job it supports, and an observable sign that it works. A technology preference is a constraint when the user states it; it is not evidence that the project succeeds.

Capture the smallest useful first deliverable, exclusions, and fixed constraints. Identify consequential uncertainty: missing data, stakeholder disagreement, platform requirements, or a hypothesis about use. Ask only questions whose answers would change scope or the next action; otherwise state a reversible assumption and proceed.

Define the project philosophy in practical terms: which tradeoff matters most, what evidence will justify progress, what failure is unacceptable, and how decisions can be revised. Avoid assigning a philosophical school unless the actual work calls for one. Make conflicts explicit: “fast first release” and “all planned integrations” may require a scope choice.

Produce a short project brief with goal, users, first deliverable, constraints, acceptance criteria, assumptions to check, and the next decision. Acceptance criteria should describe observable behavior and user outcomes, not merely files created, tools used, or a task count. Keep preferences separate from externally verified facts.

If asked to save the brief, use a project document appropriate to the repository. Preserve existing guidance; do not replace AGENTS.md or change code, deployment, or agent settings simply because a brief mentions them.

# Socratic Inquiry

Turn an attractive but vague claim into a defensible working statement. This adapts the examination of definitions in Plato's dialogues; it does not claim access to the historical Socrates.

## Method

Identify the claim doing the most work and the user's purpose in asserting it. Separate an example of a concept from a definition of the concept. Reconstruct the strongest plausible version before challenging it.

Test the proposed definition against an ordinary positive case, an ordinary negative case, and a boundary case. Look for inconsistent commitments: would the same rule be accepted in a relevantly similar case? Explain exactly which premise a counterexample undermines. A person's inability to answer is not evidence that the opposite position is true.

In dialogue, ask one consequential question at a time and use the answer to revise the next question. Do not quiz the user indefinitely or disguise a predetermined conclusion as a question. When the user requests a finished analysis, perform the examination within the answer instead of withholding the deliverable pending a conversation.

Offer a narrower claim that survives the tests, distinguish remaining uncertainty from contradiction, and connect the revised claim to the actual decision. Stop when the clarification is sufficient to act, or when new evidence rather than more questions is needed.

## Useful output

Give the original claim, the assumption exposed by the strongest counterexample, a revised working definition, and the practical implication. Use this structure only where it helps.

## Worked application — original example

Request: “Productive employees send more messages. Build a performance metric.”
A useful counterexample is the engineer who resolves an outage with few messages versus someone who floods chat without resolving it. Message volume can measure communication activity, but it cannot by itself define productive contribution. Recommend a role-specific outcome measure with context and review; treat message volume as diagnostic evidence only.

## Failure checks

Have you attacked a weak version rather than the actual claim? Have you mistaken skepticism for a conclusion? Does the user have a usable revised requirement?

## Boundaries

Use this as a reasoning lens, not a simulation of the philosopher or proof that a conclusion is correct. Follow the user's requested deliverable and constraints. Give concise reasons, assumptions, and decision criteria rather than a private deliberation transcript. Do not invent quotations, sources, historical positions, motives, or numerical evidence. Distinguish facts supplied by the user from hypotheses and value judgments. Historical claims require a checked source when precision matters; contemporary applications below are our adaptations. A lens supplies no authority to take external actions.

Scale the method to the stakes. For a simple request, use only the move that changes the answer. If the method adds no useful distinction, say so and complete the task directly. End with a usable answer or next action, not philosophy vocabulary alone.
